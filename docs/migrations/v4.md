# v4 Migration Guide

The v4 release changes how reusable workflows read their argument, flag and
path-list inputs. Every ordinary input now reaches its shell step through an
`env:` mapping and is split into an explicit array, instead of being
interpolated into the shell script before bash parses it.

The practical effect: an input's value is data the command receives, not shell
text. It cannot execute a command, change the command's syntax, or be expanded
by the shell.

Most callers need no change. Work through the sections below if you pass any of
the affected inputs.

## Affected inputs

| Workflow                    | Inputs                                                          |
| --------------------------- | --------------------------------------------------------------- |
| `run-go-ci.yml`             | `test-flags`, `codecov-files`                                   |
| `release-go-binaries.yml`   | `goreleaser-args`                                               |
| `run-rust-ci.yml`           | `test-args`, `clippy-args`, `extra-components`, `codecov-files` |
| `release-rust-binaries.yml` | `build-args`                                                    |
| `run-zig-ci.yml`            | `fmt-paths`, `cross-targets`                                    |
| `release-zig-binaries.yml`  | `targets`                                                       |

A plain space-separated value such as `-race`, `release --clean` or
`-D warnings` behaves exactly as before. Splitting is still on whitespace, and
quoting inside the value is still unsupported: `--foo "a b"` has always
tokenized to `--foo`, `"a`, `b"`, and still does.

## The shell no longer expands these values

Anything the shell used to expand at the point of substitution now arrives
literally.

| You passed              | v3 behavior                      | v4 behavior      | Do instead                                     |
| ----------------------- | -------------------------------- | ---------------- | ---------------------------------------------- |
| `--config cfg/*.yml`    | Expanded to matching files       | Passed literally | Name the file, or let the tool glob            |
| `--config $CONFIG`      | Expanded to the variable's value | Passed literally | Set the input from the caller's own expression |
| `--tag $(git describe)` | Ran the command                  | Passed literally | Compute it in the caller and pass the result   |
| `--config ~/cfg.yml`    | Expanded to the home directory   | Passed literally | Use an absolute path or `${HOME}`              |

Set the value from the calling workflow, where the expression is evaluated
before the input is passed:

```yaml
jobs:
  release:
    uses: cboone/gh-actions/.github/workflows/release-go-binaries.yml@v4.0.0
    with:
      goreleaser-args: release --clean --config ${{ vars.GORELEASER_CONFIG }}
```

## Multi-line values are rejected

These inputs are split with `read -r -a`, which stops at the first newline. A
multi-line value previously lost every line after the first without reporting
anything. It now fails the step:

```text
::error::goreleaser-args must be a single line of space-separated arguments
```

If you wrote a value as a YAML block scalar, fold it onto one line:

```yaml
# Fails in v4
with:
  goreleaser-args: |
    release
    --clean

# Correct
with:
  goreleaser-args: release --clean
```

A folded scalar (`>-`) still works, because YAML collapses it to a single line.

## Empty target lists fail with a diagnostic

`run-zig-ci.yml`'s `cross-targets` and `release-zig-binaries.yml`'s `targets`
previously iterated an empty list when given an empty or whitespace-only value.
Both now stop with a diagnostic naming the input:

```text
::error::targets must contain at least one target triple
```

What that replaces differs by workflow. `run-zig-ci.yml` built nothing and
reported success, so a cross-compile job could pass without compiling anything.
`release-zig-binaries.yml` did fail, but only later and obscurely: the build
loop produced no archives, and the checksum step then reported
`shasum: *: No such file or directory`.

Pass at least one target triple. On `run-zig-ci.yml`, turn the job off with
`run-cross-compile: false` rather than emptying its input;
`release-zig-binaries.yml` has no such toggle, so stop calling the workflow.

`run-rust-ci.yml`'s `extra-components` behaves the same way. Its step is
already skipped when the input is empty, so this affects only a value that is
entirely whitespace, which previously reached `rustup component add` with no
components for it to reject.

## Paths with spaces now work

`codecov-files` is quoted end to end, so a coverage path containing spaces is
passed as one argument. It previously split into several and broke the command.
No action is needed; this only removes a restriction.

## Zig manifest formatting

Also in v4, from [#106](https://github.com/cboone/gh-actions/issues/106):
`run-zig-ci.yml` format-checks `build.zig.zon` alongside `build.zig` and `src`.
A repository whose manifest is unformatted or missing now fails the default
formatting job. Run `zig fmt build.zig.zon`, or set `fmt-paths` to the paths
your layout uses.

## Notes

Nothing in this release renames or removes an input, an action or a workflow,
so no `uses:` string changes beyond the version tag.

Consumers that pin by full commit SHA, which this project's pinning policy
requires, take these changes only when they deliberately move the pin.
