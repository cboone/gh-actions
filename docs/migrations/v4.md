# v4 Migration Guide

The v4 release changes how reusable workflows read their argument, flag and
path-list inputs. Every ordinary input now reaches its shell step through an
`env:` mapping and is split into an explicit array, instead of being
interpolated into the shell script before bash parses it.

The practical effect: an input's value is data the command receives, not shell
text. It cannot execute a command, change the command's syntax, or be expanded
by the shell.

Most callers need no change. Work through the sections below if you pass any of
the affected inputs.

## Affected inputs

| Workflow                    | Inputs                                                          |
| --------------------------- | --------------------------------------------------------------- |
| `run-go-ci.yml`             | `test-flags`, `codecov-files`                                   |
| `release-go-binaries.yml`   | `goreleaser-args`                                               |
| `run-rust-ci.yml`           | `test-args`, `clippy-args`, `extra-components`, `codecov-files` |
| `release-rust-binaries.yml` | `build-args`                                                    |
| `run-zig-ci.yml`            | `fmt-paths`, `cross-targets`                                    |
| `release-zig-binaries.yml`  | `targets`                                                       |

A plain space-separated value such as `-race`, `release --clean` or
`-D warnings` behaves exactly as before. Splitting is still on whitespace, and
quoting inside the value is still unsupported: `--foo "a b"` has always
tokenized to `--foo`, `"a`, `b"`, and still does.

## The shell no longer expands these values

Anything the shell used to expand at the point of substitution now arrives
literally.

| You passed              | v3 behavior                      | v4 behavior      | Do instead                                     |
| ----------------------- | -------------------------------- | ---------------- | ---------------------------------------------- |
| `--config cfg/*.yml`    | Expanded to matching files       | Passed literally | Name the file, or let the tool glob            |
| `--config $CONFIG`      | Expanded to the variable's value | Passed literally | Set the input from the caller's own expression |
| `--tag $(git describe)` | Ran the command                  | Passed literally | Compute it in the caller and pass the result   |
| `--config ~/cfg.yml`    | Expanded to the home directory   | Passed literally | Use an absolute path or `${HOME}`              |

Set the value from the calling workflow, where the expression is evaluated
before the input is passed:

```yaml
jobs:
  release:
    uses: cboone/gh-actions/.github/workflows/release-go-binaries.yml@v4.1.0
    with:
      goreleaser-args: release --clean --config ${{ vars.GORELEASER_CONFIG }}
```

## Multi-line values are rejected

These inputs are split with `read -r -a`, which stops at the first newline. A
multi-line value previously lost every line after the first without reporting
anything. It now fails the step:

```text
::error::goreleaser-args must be a single line of space-separated arguments
```

If you wrote a value as a YAML block scalar, fold it onto one line:

```yaml
# Fails in v4
with:
  goreleaser-args: |
    release
    --clean

# Correct
with:
  goreleaser-args: release --clean
```

A folded scalar (`>-`) still works, because YAML collapses it to a single line.

## Empty target lists fail with a diagnostic

`run-zig-ci.yml`'s `cross-targets` and `release-zig-binaries.yml`'s `targets`
previously iterated an empty list when given an empty or whitespace-only value.
Both now stop with a diagnostic naming the input:

```text
::error::targets must contain at least one target triple
```

What that replaces differs by workflow. `run-zig-ci.yml` built nothing and
reported success, so a cross-compile job could pass without compiling anything.
`release-zig-binaries.yml` did fail, but only later and obscurely: the build
loop produced no archives, and the checksum step then reported
`shasum: *: No such file or directory`.

Pass at least one target triple. On `run-zig-ci.yml`, turn the job off with
`run-cross-compile: false` rather than emptying its input;
`release-zig-binaries.yml` has no such toggle, so stop calling the workflow.

`run-rust-ci.yml`'s `extra-components` behaves the same way. Its step is
already skipped when the input is empty, so this affects only a value that is
entirely whitespace, which previously reached `rustup component add` with no
components for it to reject.

## Paths with spaces now work

`codecov-files` is quoted end to end, so a coverage path containing spaces is
passed as one argument. It previously split into several and broke the command.
No action is needed; this only removes a restriction.

## Zig manifest formatting

Also in v4, from [#106](https://github.com/cboone/gh-actions/issues/106):
`run-zig-ci.yml` format-checks `build.zig.zon` alongside `build.zig` and `src`.
A repository whose manifest is unformatted or missing now fails the default
formatting job. Run `zig fmt build.zig.zon`, or set `fmt-paths` to the paths
your layout uses.

## Rust tool versions now need their checksums

Also in v4, from [#61](https://github.com/cboone/gh-actions/issues/61):
`run-rust-ci.yml`'s `audit-version` and `llvm-cov-version` become genuinely
settable, and a caller who pinned either one has to act.

cargo-audit and cargo-llvm-cov publish no checksum file upstream, so this
repository commits their SHA-256 digests. Through v3 a guard refused every
version but the one those digests covered, which meant each input accepted
exactly one value, the one it already defaulted to:

```text
::error::Unsupported cargo-llvm-cov version: 0.9.0
Checksums are only available for v0.8.5.
```

There was no way to move off the shipped version, and no way to stay behind it
once the default moved. Each input now has a companion,
`audit-checksums` and `llvm-cov-checksums`, holding one
`<sha256>  <version>  <target triple>` line per platform, so passing a version
means passing its digests with it.

**If you passed either input explicitly**, the simplest fix is to drop it and
take the default, which is the newest version this repository ships digests
for:

```yaml
# Fails in v4: 0.8.5 has no matching checksum line
with:
  coverage: true
  llvm-cov-version: 0.8.5

# Correct: take the default
with:
  coverage: true
```

To stay on the older version instead, pass its digests. These are the v3
values, for the four supported targets:

```yaml
with:
  coverage: true
  llvm-cov-version: 0.8.5
  llvm-cov-checksums: |
    7e62d664f5133d43d33a3b11138c93feff98bd71e953ddc260ea8ddf360a37c6  0.8.5  x86_64-unknown-linux-gnu
    8248a6d5dcb47307c2ef6d5815f90bca07d04a6f1acd06b658f689cb2d8247d9  0.8.5  aarch64-unknown-linux-gnu
    b8598f0ea19900f6dea3b3fd4214f1de96f1bff47eaa32a775643fc402cabad0  0.8.5  x86_64-apple-darwin
    816b6ff2c23ba569327d153189d7434afd501fc873cc0f5fbb0cfe412b97bc22  0.8.5  aarch64-apple-darwin
```

The same applies to `audit-version` and `audit-checksums`. cargo-audit v0.22.1's
digests were `1890badd5f15831a9af4b074399fcd21e6f7c0fe42c84e9254cdffc9f813765c`,
`4c8df835ee484441bd2c8c6bcac28c4ce4b4058ba9e7477cb9e0012fe7769f66`,
`582d104a2a4bdb127c6bf6d056d89eede40686d11f52e4bc1765132ec99d2fca` and
`04e76e1da25f597bea4814c44faf8aac215838b9f3646e3b6a873d87acd31b73`, in that
same target order.

For any other version, read the digests from the release's asset metadata and
check them against the downloaded archives:

```bash
gh api repos/taiki-e/cargo-llvm-cov/releases/tags/v0.9.1 \
  --jq '.assets[] | "\(.digest | sub("^sha256:"; ""))  \(.name)"'

gh api repos/rustsec/rustsec/releases/tags/cargo-audit%2Fv0.22.2 \
  --jq '.assets[] | "\(.digest | sub("^sha256:"; ""))  \(.name)"'
```

Entries are keyed by version as well as target because cargo-llvm-cov's archive
name carries no version, so a file name alone cannot tell two releases apart. A
version with no matching line is refused before anything is downloaded, rather
than verified against another release's digest.

## `reuse lint` reports more than it used to

Also in v4, from [#61](https://github.com/cboone/gh-actions/issues/61):
`actions/run-reuse` installs reuse 6.2.0, up from 5.0.2.

This one has no opt-out. `run-reuse` exposes `uv-version` and `args` but no
reuse version, because it installs from this repository's hash-pinned
`requirements/reuse.txt`. Staying on 5.x means pinning the action itself to a
v3 tag.

A repository that passed `reuse lint` at 5.0.2 can fail at 6.2.0 for three
reasons, none of which is a change in what REUSE requires:

| Change                                                            | What it can surface                                                | What to do                                                                       |
| ----------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| `lint` reads whole files, where 5.x stopped after the first 4 KiB | Copyright or license text deep in a file, now found and attributed | Wrap the passage in `REUSE-IgnoreStart` and `REUSE-IgnoreEnd`                    |
| A new **Invalid SPDX License Expressions** criterion              | An expression that is not valid SPDX grammar, previously ignored   | Correct the expression, or the license identifier it names                       |
| **Bad licenses** now considers only `LICENSES/`                   | Nothing new; this narrows what is reported                         | No action. A repository relying on it flagging files elsewhere loses that signal |

The first is the one that bites. It is not a stricter rule, only a wider
search: text that always looked like REUSE information is now read, wherever
it sits in the file. Vendored headers, license blocks quoted inside
documentation and test fixtures are the usual sources.

Encoding detection also changed. reuse 6 requires `python-magic`, a `ctypes`
wrapper around the runner image's `libmagic`, and falls back to another module
when that import fails. `requirements/reuse.in` asks for
`reuse[charset-normalizer]` so a fallback is always installed, but detection
can still differ between a runner that supplies `libmagic` and one that does
not. Set `REUSE_ENCODING_MODULE` if your jobs need it to agree:

```yaml
- uses: cboone/gh-actions/actions/run-reuse@v4.1.0
  env:
    REUSE_ENCODING_MODULE: charset_normalizer
```

## Notes

Nothing in this release renames or removes an input, an action or a workflow,
so no `uses:` string changes beyond the version tag. The Rust checksum inputs
above are additions; what changed is that their version inputs now accept more
than one value.

Consumers that pin by full commit SHA, which this project's pinning policy
requires, take these changes only when they deliberately move the pin.
